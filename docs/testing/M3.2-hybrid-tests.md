# M3.2 Hybrid Limiter Test Plan

## Scope

Validate hybrid semantics (Strict AND, Option A2 ordering) and failure policy toggle.

## Recommended test scaffolding

- Use a fake local limiter with deterministic decisions:
  - returns Allow or Deny with configurable retry_after
- Use a fake backend or fake distributed limiter:
  - returns Allow / Deny / Err deterministically
  - supports artificial delay to test ordering/head-start

## Tests (minimum set)

### Semantics

1. local=Allow, dist=Allow => Allow
2. local=Deny(10ms), dist=Allow => Deny(10ms)
3. local=Allow, dist=Deny(20ms) => Deny(20ms)
4. local=Deny(10ms), dist=Deny(20ms) => Deny(20ms) (max)
5. retry_after max logic matches HierarchicalLimiter behavior

### Ordering and latency behavior (Option A2)

1. dist has 100ms delay, local denies immediately:
   - hybrid returns quickly (does not await dist)
2. dist started before local check:
   - measure that total time for (local allow + dist delay) is ~dist delay not (local + dist) delay
   - (in unit tests, check ordering via fake that records “started” timestamp before local check)

### Failure policy toggle

1. dist error + FailOpen => Allow (with event/metric)
2. dist error + FailClosed => Deny(50ms)
3. Ensure policy is configurable via hybrid config

### Instrumentation pass-through

1. When instrumentation enabled, hybrid emits OperationCompleted (and/or additional events for backend error)
2. Ensure decisions are cloned/emitted consistently

## Integration tests (optional / later)

- With Redis backend running:
  - simulate backend unavailable and confirm FailOpen vs FailClosed behavior
